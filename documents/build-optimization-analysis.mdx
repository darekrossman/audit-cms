# Build Optimization Analysis

## Overview

This analysis examines build performance issues across all web applications in the monorepo and provides a comprehensive optimization plan covering code-level fixes, infrastructure enhancements, and tooling upgrades.

**Current State**: Next.js 14.2.35, pnpm workspaces, no task runner, Webpack bundler

***

# Part 1: Identified Bottlenecks

## 1.1 MAX\_RECORDS \= 750 Causing API Response Size Errors

**Problem**: Contentful API responses can exceed the 7MB limit when fetching 750 records with resolved references.

**Locations**:

| File                                           | Line | Value                     |
| ---------------------------------------------- | ---- | ------------------------- |
| `packages/helper-contentful/src/contentful.ts` | 74   | `const MAX_RECORDS = 750` |
| `shared-contentful-helpers.js`                 | 4    | `const MAX_RECORDS = 750` |

**Root Cause**: Algolia build scripts call `getPagesForAlgolia()` with `include: 3`:

```javascript
// shared-contentful-helpers.js:244-264
async function getPagesForAlgolia(websiteId, locale, includeContent, overrideConfig) {
  const results = await getPagedRecords({
    content_type: 'page',
    include: includeContent ? 3 : 1,  // 3 levels of nested references
    ...
  })
}
```

When `includeContent: true`, fetching 750 pages with 3 levels of nested references exceeds Contentful's 7MB response limit.

**Impact**: Build failures during Algolia indexing (primarily affects web-mx due to content volume).

***

## 1.2 Deep Include Levels Causing Circular References

**Problem**: Include levels of 4-5 resolve excessive nested references, creating circular dependency chains and bloated payloads.

**Location**: `packages/helper-contentful/src/contentful.ts:63-72`

```typescript
export enum ContentfulIncludeLevelEnum {
  GENERAL = 5,   // Deep nesting - PRIMARY ISSUE
  CATEGORY = 4,
  TOPIC = 4,
  PAGE = 5,      // Deep nesting - PRIMARY ISSUE
  BLOG = 4,
  GIG = 3,
  LINKS = 2,
  BASE = 0,
}
```

**Circular Reference Chain**:

```
Page (include=5)
  -> UISection (level 1)
    -> UIButton with href to another Page (level 2)
      -> That Page's sections (level 3)
        -> More buttons/links (level 4)
          -> More pages (level 5) <- CIRCULAR BACK TO ORIGINAL
```

**Content Type Relationships Causing Cycles**:

| Cycle                    | Path                                                                             |
| ------------------------ | -------------------------------------------------------------------------------- |
| Page -> Section -> Page  | Pages contain UIMulticolumnSection which can embed buttons linking back to pages |
| Blog -> Category -> Blog | Blog posts reference categories; categories can reference featured blog posts    |
| Blog -> Topic -> Blog    | Topics link to all posts using that topic via `links_to_entry` queries           |

**Impact**:

* JSON payloads bloated with redundant nested data
* Memory pressure during build
* Potential serialization errors in Next.js SSG
* Slow page generation

***

## 1.6 No Build Caching or Task Orchestration

**Problem**: The monorepo uses pnpm workspaces without a task runner.

```yaml
# pnpm-workspace.yaml
packages:
  - 'packages/*'
```

Each `pnpm -F 'web-*' run build` rebuilds from scratch with no caching between builds or across CI runs.

## Code-Level Fixes

### Fix 1: Reduce MAX\_RECORDS from 750 to 100

**Change Locations**:

* `packages/helper-contentful/src/contentful.ts:74`
* `shared-contentful-helpers.js:4`

**Impact**:

| Metric                  | Before (750) | After (100) | Change    |
| ----------------------- | ------------ | ----------- | --------- |
| Records per API request | 750          | 100         | -87%      |
| Estimated response size | 7MB+         | \~1MB       | -85%      |
| API calls for 500 items | 1            | 5           | +400%     |
| 7MB limit exceeded      | Frequent     | Never       | **Fixed** |

**Risk**: More API calls needed, but each stays within limits.

**Priority**: **P0** - Directly fixes Algolia build failures.

***

### Fix 2: Reduce GENERAL and PAGE from 5 to 3

**Change Location**: `packages/helper-contentful/src/contentful.ts:63-67`

```typescript
// Before
GENERAL = 5,
PAGE = 5,

// After
GENERAL = 3,
PAGE = 3,
```

**Impact**:

| Metric                   | Include\=5 | Include\=3 | Change    |
| ------------------------ | ---------- | ---------- | --------- |
| Nesting depth            | 5 levels   | 3 levels   | -40%      |
| Avg payload size         | \~150KB    | \~50KB     | -67%      |
| Circular ref probability | High       | Low        | -80%      |
| Build memory usage       | High       | Moderate   | -50% est. |

**Risk**: Low - most UI sections only need 2-3 levels of nesting.

**Priority**: **P0** - High impact across all apps.

***

### Fix 3: Reduce blogPost Homepage Include to LINKS (2)

**Change Location**: `packages/dls/src/content/blogPost.ts:42`

```typescript
// Before
ContentfulIncludeLevelEnum.GENERAL,  // 5

// After
ContentfulIncludeLevelEnum.LINKS,    // 2
```

**Rationale**: The `select` clause already limits returned fields - deep includes are unnecessary.

**Priority**: **P1** - Safe change, benefits all apps with blogs.

### Fix 4: Implement Homepage Caching During Build

**Problem**: \~9,774+ redundant homepage fetches during builds.

**Solution**: Cache homepage per locale at build start:

```typescript
const homepageCache = new Map<string, ContentfulBlogHomepage>()

async function getCachedBlogHomepage(websiteId: string, locale: string, isPreview: boolean) {
  const cacheKey = `${websiteId}_${locale}`
  if (!homepageCache.has(cacheKey)) {
    const homepage = await getBlogHomePage(websiteId, locale, isPreview, '', ContentfulIncludeLevelEnum.LINKS)
    homepageCache.set(cacheKey, homepage)
  }
  return homepageCache.get(cacheKey)
}
```

**Impact**: Reduce homepage API calls from thousands to 6 (one per locale).

**Priority**: **P1** - High impact for blog-heavy apps.

**Note**: This manual caching would be superseded by Next.js 16 Cache Components (`"use cache"` directive).

***

## Infrastructure Enhancements

### Enhancement 1: Vercel Enhanced Build Machines

Enhanced machines provide 2x the resources of standard machines:

| Machine Type | vCPUs | Memory | Disk  | Cost (Pro)           |
| ------------ | ----- | ------ | ----- | -------------------- |
| Standard     | 4     | 8 GB   | 23 GB | $0.014/min on-demand |

**Configuration**: Project Settings → Build and Deployment → Build Machine Type

**Priority**: **P0** - Configuration change only, immediate benefit.

### Enhancement 2: Turborepo Integration

**What Turborepo Provides**:

* **Incremental builds**: Only rebuilds changed packages
* **Remote caching**: Share build artifacts across CI runs and team members (automatic on Vercel)
* **Task orchestration**: Parallel execution with dependency awareness

**Proposed Configuration** (`turbo.json`):

```json
{
  "$schema": "https://turbo.build/schema.json",
  "globalDependencies": [".env", ".nvmrc"],
  "globalEnv": [
    "NODE_ENV",
    "CONTENTFUL_SPACE_ID",
    "CONTENTFUL_DELIVERY_API_KEY",
    "CONTENTFUL_PREVIEW_API_KEY",
    "ALGOLIA_APP_ID",
    "ALGOLIA_ADMIN_KEY"
  ],
  "tasks": {
    "build": {
      "dependsOn": ["^build"],
      "outputs": [".next/**", "!.next/cache/**"],
      "env": ["WEBSITE_ID", "ANALYZE", "CF_PAGES"]
    },
    "dev": {
      "cache": false,
      "persistent": true
    },
    "test": {
      "dependsOn": ["^build"],
      "outputs": ["coverage/**"]
    }
  }
}
```

**Migration Steps**:

1. Install Turborepo:
   ```bash
   pnpm add -D turbo -w
   ```
2. Add `turbo.json` to root
3. Update `package.json` scripts:
   ```json
   {
     "scripts": {
       "build": "turbo run build",
       "build:web-mx": "turbo run build --filter=web-mx",
       "dev:web-mx": "turbo run dev --filter=web-mx"
     }
   }
   ```
4. For local development, authenticate for remote cache:
   ```bash
   npx turbo login
   npx turbo link
   ```

**Priority**: **P1** - Medium effort, high impact for CI/CD.

### Enhancement 3: Next.js Upgrade + Turbopack

**Turbopack Timeline**:

| Version                   | Turbopack Status     | Notes                                       |
| ------------------------- | -------------------- | ------------------------------------------- |
| Next.js 15 (Oct 2024)     | Dev stable           | `next dev --turbo` ready for production use |
| Next.js 15.3 (Apr 2025)   | Build alpha          | 99% test pass rate; staging/preview only    |
| Next.js 15.5 (Aug 2025)   | Build beta           | 2-5x faster builds                          |
| **Next.js 16 (Oct 2025)** | **Stable & default** | No flags needed                             |

**Current vs. Target**:

| Aspect        | Current (14.2.35) | Target (16.x)         |
| ------------- | ----------------- | --------------------- |
| Bundler       | Webpack           | Turbopack (default)   |
| Build caching | None              | File system cache     |
| Development   | Webpack HMR       | Turbopack incremental |

**Turbopack Characteristics**:

* Incremental computation with function-level caching
* Lazy bundling (only bundles what's requested)
* File system caching persists compiled artifacts across builds

**webpack to Turbopack Migration**:

Current `next.config.js` uses custom webpack:

```javascript
// packages/web-mx/next.config.js
webpack: (config) => {
  config.module.rules.push({
    test: /@doordash\//,
    sideEffects: false,
  })
  return config
}
```

Turbopack equivalent:

```javascript
const nextConfig = {
  turbopack: {
    rules: {
      // Turbopack uses loaders instead of webpack plugins
    },
  },
  // Tree-shaking is automatic in Turbopack
}
```

**Upgrade Path** (incremental adoption):

1. **Now (14.2.35 → 15.x)**: Upgrade to Next.js 15, enable `next dev --turbo` for development
2. **After testing**: Try `next build --turbopack` in staging/preview (beta in 15.5+)
3. **Full migration**: Upgrade to Next.js 16 where Turbopack is default

```bash
# Next.js 15: Test Turbopack incrementally
next dev --turbo         # Development (stable)
next build --turbopack   # Production builds (beta in 15.5+)

# Fallback available in Next.js 15
next dev --webpack
next build --webpack

# Next.js 16: Turbopack is default, no flags needed
next dev
next build
```

**Compatibility Notes**:

**Supported**:

* Styled Components (`compiler.styledComponents: true`)
* SASS/SCSS
* CSS Modules
* TypeScript/JSX
* Bundle analyzer

**Requires attention**:

* Custom webpack rules need conversion to Turbopack loaders
* `transpilePackages` behavior may differ
* Some webpack plugins may not have equivalents

**Priority**: **P2-P3** - Medium-high effort, significant long-term benefit.

### Enhancement 4: Next.js 16 Static Generation Improvements

**Single-Pass Static Generation**: Next.js 16 reuses the first render instead of rendering twice (once for data, once for HTML).

**Shared Fetch Cache**: Static generation workers share fetch cache across pages:

```
Current: 1,570 posts × 6 locales × 4 API calls = ~37,680 calls
With shared cache: ~6 homepage calls + ~1,570 unique post calls = ~1,576 calls
```

**Cache Components** (`"use cache"` directive):

```typescript
async function getCachedBlogHomepage(websiteId: string, locale: string) {
  "use cache"
  cacheLife('hours')
  cacheTag(`homepage-${locale}`)
  return await getBlogHomePage(websiteId, locale)
}
```

This would replace manual homepage caching (Fix 4) with a framework-native solution.

# Part 5: Risks & Mitigations

## Turbopack Compatibility

**Risk**: Custom webpack configuration may not translate directly.

**Mitigation**:

* Test with `--turbopack` flag before full migration
* Keep `--webpack` fallback available
* Audit custom loaders and plugins

## Cache Invalidation

**Risk**: Stale Turborepo cache causing incorrect builds.

**Mitigation**:

* Configure `globalEnv` in turbo.json with all environment variables that affect builds
* Use environment-specific cache keys
* Document cache purging: `turbo run build --force`

## Breaking Changes

**Risk**: Next.js 16 introduces breaking changes.

**Mitigation**:

* Follow official upgrade guide
* Run Next.js codemods
* Regression test each app

## Include Level Reduction

**Risk**: Deeply nested content may not render correctly with include\=3.

**Mitigation**:

* Visual regression test all page types
* Add content-type specific overrides for edge cases
* Monitor for missing data errors
