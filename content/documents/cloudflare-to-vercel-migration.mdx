# Cloudflare to Vercel Edge Migration

## Overview

This document assesses migrating the web applications from a two-tier Cloudflare → Vercel architecture to Vercel-only, eliminating Cloudflare as the front proxy layer.

---

## Current Architecture

```
Internet
   │
   ▼
┌─────────────────────────────────────────────────────────┐
│  CLOUDFLARE EDGE                                        │
│  • TLS termination                                      │
│  • WAF rules (Terraform-managed)                        │
│  • DDoS protection                                      │
│  • Workers (request routing)                            │
│  • Bot detection (_cfuvid cookie)                       │
└─────────────────────────────────────────────────────────┘

   ▼
```

A captured request to `merchants.doordash.com/en-us` illustrates the current flow:

### Request Path

| Hop | Component | Evidence |
|-----|-----------|----------|
| 1 | **Cloudflare Edge** | IP: 104.18.35.30 (AS13335 CLOUDFLARENET) |
| 2 | **Vercel Edge** | `x-vercel-id: iad1:iad1::...` |

### What Cloudflare Is Doing

| Function | Header/Evidence | Value |
|----------|-----------------|-------|
| TLS Termination | Client IP | Resolves to Cloudflare, not Vercel |
| Proxy Pass-through | `cf-cache-status` | `DYNAMIC` (not caching) |
| Bot Detection | `set-cookie` | `_cfuvid` (7-day visitor ID) |
| Request Tagging | `cf-ray` | `9b849267fb35e644-IAD` |
| Server Identification | `server` | `cloudflare` |

### What Vercel Is Doing

| Function | Header/Evidence | Value |
|----------|-----------------|-------|
| ISR Cache | `x-vercel-cache` | `HIT` |
| Cache Level | `x-vercel-cache-level` | `regional` |
| Content Age | `age` | `344506` (~4 days cached) |
| Edge Runtime | `x-vercel-debug-handler-type` | `edge-runtime` |
| Warm Function | `x-vercel-debug` | `start_type=hot` |

### Latency Breakdown

**Total: 136ms**

| Phase | Time | Notes |
|-------|------|-------|
| Cloudflare proxy | ~10-20ms | Estimated overhead |
| Vercel terminator | 65ms | Edge processing |
| Router | 41ms | Request routing |
| Lambda/Middleware | 27ms | Function execution |
| Body transfer | 13ms | Compressed HTML |

### Key Observation

**Cloudflare is not caching**: `cf-cache-status: DYNAMIC`

The HTML response passes through Cloudflare without caching. All caching happens at Vercel (`x-vercel-cache: HIT`). Cloudflare adds:
- Bot detection cookie (`_cfuvid`)
- Request headers (`cf-ray`, `server`)
- Proxy latency (~10-20ms)

## Why Remove Cloudflare

### Vercel's Position

Vercel explicitly recommends against using reverse proxies in front of their platform. From the [official documentation](https://vercel.com/docs/security/reverse-proxy):

> Vercel does not recommend placing a reverse proxy server in front of your Vercel project because it negatively impacts Vercel's firewall effectiveness.

The [Cloudflare-specific guidance](https://vercel.com/kb/guide/cloudflare-with-vercel) states:

> The biggest disadvantage is that Vercel no longer has full traffic visibility, which prevents the Vercel Firewall and their threat intelligence products from working to their full potential. This includes their ability to automatically challenge requests, prevent DDoS attacks, and more.

### Documented Impacts

According to Vercel's [reverse proxy documentation](https://vercel.com/docs/security/reverse-proxy), using a proxy in front of Vercel causes four specific issues:

| Issue | Vercel Documentation |
|-------|---------------------|
| **Loss of traffic visibility** | "Vercel's CDN loses visibility into actual traffic, reducing firewall effectiveness in identifying suspicious activity" |
| **IP address masking** | "Real end-user IP addresses cannot be accurately identified, breaking threat detection mechanisms" |
| **Usage spike risk** | "If the reverse proxy undergoes a malicious attack, that traffic can be forwarded to Vercel, causing unexpected usage spikes" |
| **Cache purge limitation** | "If the reverse proxy is compromised, Vercel's firewall cannot automatically purge the cache" |

### Bot Protection Degradation

From Vercel's [Cloudflare guidance](https://vercel.com/kb/guide/cloudflare-with-vercel):

> Vercel discourages using reverse proxies (e.g., Cloudflare, Azure, or other CDNs) in front of Vercel when Bot Protection is enabled. This setup significantly degrades detection accuracy and performance, resulting in a poor end-user experience.

Specific bot protection issues documented:
- **Obscured detection signals**: "Legitimate users may be incorrectly challenged because the proxy masks signals that Bot Protection relies on"
- **IP rotation interference**: "Some proxies rotate their exit node IPs frequently, forcing Vercel to re-initiate challenges on every IP change"

### Additional Documented Concerns

| Issue | Source |
|-------|--------|
| **Caching conflicts** | "Cloudflare and Vercel both have their own caching systems, which can cause unpredictable behavior" ([source](https://vercel.com/kb/guide/cloudflare-with-vercel)) |
| **Analytics impact** | "Vercel sees Cloudflare's IP addresses, not the original visitor's IP. This impacts Vercel Analytics" ([source](https://vercel.com/kb/guide/cloudflare-with-vercel)) |
| **Performance degradation** | "The additional proxy layer introduces latency, which degrades application performance" ([source](https://vercel.com/kb/guide/cloudflare-with-vercel)) |

### What's Gained by Removing Cloudflare

| Benefit | Description |
|---------|-------------|
| **Full traffic visibility** | Vercel threat intelligence and firewall operate at full effectiveness |
| **Accurate bot detection** | BotID and Bot Protection receive unmasked client signals |
| **Real IP addresses** | Analytics, geo-blocking, and rate limiting use actual visitor IPs |
| **Reduced latency** | Eliminate proxy hop (~10-20ms observed in request analysis) |
| **Simplified caching** | Single cache layer (Vercel ISR) with predictable behavior |
| **Unified operations** | Single dashboard, consolidated billing, no Terraform repos |

## Vercel BotID (Kasada)

### Overview

BotID is Vercel's invisible bot detection solution powered by [Kasada](https://www.kasada.io/). It protects high-value routes (forms, checkouts, APIs) from automated attacks without CAPTCHAs or user friction.

### How It Works

```
1. Client loads page → BotID injects obfuscated detection code
2. User submits form → Browser includes challenge solution
3. Server calls checkBotId() → Vercel validates with Kasada ML
4. Pass/Fail verdict → Application allows or blocks request
```

Key characteristics:
- **Invisible**: No CAPTCHAs, no user interaction required
- **Adaptive**: Detection logic mutates on every page load to prevent reverse engineering
- **ML-powered**: Kasada analyzes thousands of client-side signals
- **Binary verdict**: Clear pass/fail (no scores or thresholds to tune)

### Current Implementation

BotID is already deployed across the web applications for form protection.

**Client Component** (`packages/component-ui/src/forms/botId/botIdClient.tsx`):

```typescript
import { BotIdClient } from 'botid/client'

const protectedRoutes = [
  { path: '/api/form/captcha', method: 'POST' },
]

export const DoorDashBotIdClient = () => {
  return <BotIdClient protect={protectedRoutes} />
}
```

**Server Handler** (`packages/component-ui/src/forms/botId/botIdHelpers.ts`):

```typescript
import { checkBotId } from 'botid/server'

export const checkBotIdHandler = async (req, res) => {
  const verification = await checkBotId({
    advancedOptions: {
      extraAllowedHosts: [process.env.VERCEL_BOT_ID_ALLOWED_HOST],
    },
  })

  if (verification.isBot) {
    return res.status(403).json({
      error: 'captcha',
      error_type: verification.classificationReason
    })
  }

  return res.status(200).json({ success: true })
}
```

**Routing** (`next.config.js`):

```javascript
// BotID challenge endpoint
{
  source: "/:lang/149e9513-01fa-4fb0-aad4-566afd725d1b/.../c.js",
  destination: "https://api.vercel.com/bot-protection/v1/challenge"
}

// BotID proxy endpoint
{
  source: "/:lang/149e9513-01fa-4fb0-aad4-566afd725d1b/:path*",
  destination: "https://api.vercel.com/bot-protection/v1/proxy/:path*"
}
```

**Environment Variables**:

| Variable | Purpose |
|----------|---------|
| `NEXT_PUBLIC_VERCEL_BOT_ID_ENABLED` | Enable/disable BotID |
| `VERCEL_BOT_ID_BYPASS` | Bypass for testing |
| `VERCEL_BOT_ID_ALLOWED_HOST` | Additional allowed hosts (e.g., `merchants.doordash.com`) |

### BotID with Vercel as Front Layer

Reverse proxies [significantly degrade detection accuracy and performance](https://vercel.com/kb/guide/cloudflare-with-vercel) for bot protection. When Cloudflare is removed, BotID functionality improves:

| Aspect | With Cloudflare Proxy | Vercel Direct | Source |
|--------|----------------------|---------------|--------|
| **Traffic visibility** | "Proxy masks signals that Bot Protection relies on" | Full client context
| **Detection accuracy** | "Significantly degrades detection accuracy" | Optimal signal collection
| **IP handling** | "Some proxies rotate exit node IPs frequently, forcing re-initiated challenges" | Stable client IP
| **User experience** | "Poor end-user experience" due to false positives | Legitimate users pass smoothly

## Cloudflare Stream

### Current Usage

Hero videos embedded via `@cloudflare/stream-react`.

### Post-Migration

Cloudflare Stream operates independently of the proxy architecture. Videos can be embedded directly from Cloudflare's CDN:

```
Before: Client → Cloudflare Proxy → Vercel → (video from Stream)
After:  Client → Vercel → (video direct from Stream CDN)
```

No migration required. Update embed URLs if currently routed through Workers.

## Migration Requirements

### Prerequisites

1. **Audit of existing rules** in `doordash/tf_cdn_cloudflare`
2. **DNS access** to update records

### Rules Audit

Information needed from Terraform:

| Rule Type | Count | Vercel Mapping |
|-----------|-------|----------------|
| IP blocks | ? | IP Blocking |
| Rate limits | ? | Rate Limiting Rules |
| Country blocks | ? | Custom Rule (geo condition) |
| Header matches | ? | Custom Rule |
| Bot challenges | ? | Bot Protection Ruleset |
| OWASP rules | ? | OWASP Core Ruleset |

### Migration Steps

1. **Configure Vercel WAF** (parallel with existing):
   - Enable OWASP Core Ruleset
   - Create rate limiting rules
   - Add IP blocking rules
   - Create custom rules for specific patterns
   - Enable in Log mode initially

2. **Update DNS**:
   - Point domains directly to Vercel
   - Remove Cloudflare proxy (disable orange cloud)

3. **Decommission Workers**:
   - Remove `worker-get-dd`
   - Traffic flows directly to Vercel

4. **Validate**:
   - Monitor Vercel Firewall logs
   - Compare blocked traffic patterns
   - Verify legitimate traffic not impacted

5. **Cleanup**:
   - Archive `doordash/tf_cdn_cloudflare`
   - Archive `doordash/tf_cdn_cloudflare_workers`

### OWASP Ruleset

- Less granular than Cloudflare's rule engine
- Test in Log mode before enabling Deny

- Consolidate rules if Cloudflare count exceeds limits
